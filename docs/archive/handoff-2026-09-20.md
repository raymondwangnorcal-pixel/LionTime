## 1. What LionHour is

A single-page website, `lionhour.com`, that tells Columbia students whether a campus venue
is open right now. 43 venues across five categories — libraries, dining halls, cafes,
fitness, student services — plus dining-hall menus. Live hours are scraped on a schedule,
published to an API, and rendered client-side with countdown timers. Operated by Gapless
Labs (Raymond's studio); a sponsorship/ad-sales business is being designed on top of it
but is **not built**.

- Repo: `https://github.com/raymondwangnorcal-pixel/LionTime` (public)
- Local checkout: `~/PersonalProjects/Gapless-Labs/InternalProjects/LionTime`
  (`~/PersonalProjects/LionTime` exists but is **empty** — ignore it)
- Hosting: Vercel, apex `lionhour.com` primary, `www` 308-redirects to apex
- State store: Upstash Redis
- Control plane: a dedicated Telegram bot ("Lion Hour"), webhook at `/api/telegram`

### The three rules that explain most of the codebase

1. **`VENUES` in `index.html` is the single source of truth** (DEC-0068). It starts at
   `index.html:1090`. Every derived artifact — `lib/venue-catalog.generated.mjs`,
   `lib/preview-summary.generated.mjs`, `sitemap.xml`, the 49 static pages under `hours/` —
   is generated at build time by `npm run build` (`scripts/build.mjs`). Never hand-edit a
   generated file.
2. **A publish is not done until the site is serving it** (DEC-0072). Every hours workflow
   reads the PUT's HTTP status code (a 3xx is a failure, because curl does not follow
   redirects) and then re-fetches the endpoint and compares the `generated` stamp.
   `lib/publish-verification.js` / `scripts/verify-published-snapshot.mjs`.
3. **Audit what the site serves, not whether the job ran** (DEC-0073). `Audit published
   hours` reads all five public endpoints four times a day and complains about stale or
   empty snapshots regardless of whether every job was green. Born from two incidents where
   every workflow was green while the site served frozen or blank data for days.

`docs/decisions.md` is the decision ledger — DEC-0001..DEC-0075, each with
rationale, scope, and implementation status. 74 are committed; DEC-0075 is still in the
uncommitted diff (2.2). **Read the last ~15 before changing anything
structural.** New decisions get appended in the same shape.

## 3. Architecture

### 3.1 Shape of the thing

```
index.html (2,114 lines)      the whole site: VENUES array + UI + status/countdown logic
  assets/*.js                 per-category browser hydration (library, dining, menus,
                              recreation, student-services, dining-vote)
  hours/*.html (49)           generated static per-venue SEO pages
  sitemap.xml, robots.txt     generated; robots disallows /api/ and /qr/

api/*.js (11 routes)          Vercel functions; GET public, PUT authenticated
  library-hours, dining-hours, barnard-dining-hours, recreation-hours,
  student-services-hours, dining-menus     -> the six published feeds
  dining-vote, qr, qr-stats, preview, telegram

lib/*.js                      per-feed schema / service / store / resolver / parser,
                              plus hours-audit, publish-verification, autofix-*,
                              telegram-*, and the two *.generated.mjs build outputs

scripts/*.mjs|*.py            scrapers, build, SEO generation, audit, autofix, verification
tests/*.test.mjs|test_*.py    460 tests
docs/                         decisions ledger + per-pipeline operations docs + designs
```

Each hours feed follows the same spine: **scraper → schema validation → PUT to its API
route → Upstash → verification that the site serves it → resolver + browser hydration**,
with an embedded baseline in `VENUES` as the fallback when a live feed is unavailable.
